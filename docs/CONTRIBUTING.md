# แนวทางการพัฒนา WalaiTrack

เอกสารนี้รวมข้อตกลงของทีม กฎทางธุรกิจ และกับดักที่เคยเจอมาแล้ว
อ่านก่อนเริ่มเขียนโค้ดครั้งแรก และย้อนมาดูเวลาติดปัญหา

---

## บริบทของโปรเจกต์

- เป็นงานนักศึกษา ไม่ใช่ระบบ production ทีมมี 6 คน ระดับความรู้ไม่เท่ากัน
- ผู้ใช้หลักคือ **เจ้าหน้าที่ศูนย์รับบริจาคและศูนย์พักพิง** เป็น internal tool
  ส่วนประชาชนทั่วไปใช้ได้เฉพาะฟอร์มสาธารณะ 2 หน้า
- ทุกคนต้อง **อธิบายโค้ดของตัวเองด้วยปากเปล่าได้** ตอนสอบ
  จึงเลือกวิธีที่ตรงไปตรงมาแม้จะยาวกว่า ดีกว่าโค้ดสั้นที่อ่านยาก
  และเขียนคอมเมนต์ภาษาไทยในจุดที่เหตุผลไม่ชัดเจนจากตัวโค้ด

## โครงสร้างที่ทุกฟีเจอร์ใช้เหมือนกัน

แต่ละฟีเจอร์อยู่ใน `app/<ชื่อฟีเจอร์>/`

| ไฟล์ | หน้าที่ |
|---|---|
| `page.tsx` | Server Component ดึงข้อมูลมาแสดง (Read) |
| `actions.ts` | Server Action สำหรับ Create / Update / Delete |
| `xxx-form.tsx` | Client Component ฟอร์มกรอกข้อมูล |
| `xxx-button.tsx` | Client Component ปุ่มที่ต้องมี onClick |

ดูตัวอย่างที่ `app/donors/` ใช้เป็นแม่แบบได้

**ไฟล์ของกลาง ห้ามแก้โดยไม่แจ้งทีม**
`lib/supabase/client.ts` · `lib/supabase/server.ts` · `lib/supabase/proxy.ts` · `proxy.ts`

## ฐานข้อมูล

ตารางหลัก

| ตาราง | เก็บอะไร |
|---|---|
| `centers` | ศูนย์รับบริจาค (`warehouse`) และศูนย์พักพิง (`shelter`) |
| `profiles` | ผู้ใช้ระบบ ต่อจาก `auth.users` มี `role` (`admin`/`staff`/`volunteer`) และ `center_id` |
| `donors` | ทะเบียนผู้บริจาค |
| `donations` | ล็อตของที่รับเข้าคลัง มี `quantity_remaining` ที่ถูกตัดเมื่อจัดสรร |
| `requests` | คำขอจากศูนย์พักพิง มี `quantity_fulfilled` และ `status` |
| `allocations` | การจัดสรร เชื่อม `requests` กับ `donations` |

ตารางเสริม

| ตาราง | เก็บอะไร |
|---|---|
| `donation_pledges` | คำร้องแจ้งความประสงค์บริจาคจากฟอร์มสาธารณะ รอเจ้าหน้าที่ตรวจ |
| `request_pledges` | คำร้องขอความช่วยเหลือจากฟอร์มสาธารณะ รอเจ้าหน้าที่ตรวจ |
| `public_needs` | ยอดสรุปรายหมวดหมู่ที่หน้าแรกใช้แสดง อัปเดตด้วย trigger |

### กฎเหล็ก: แก้โครงสร้างฐานข้อมูลต้องเขียนเป็นไฟล์เสมอ

ถ้าจะเพิ่มหรือแก้ตาราง **ให้เขียนไฟล์ใหม่ใน `docs/sql/` แล้ว commit ขึ้น git**
ห้ามรันใน Supabase Dashboard เฉย ๆ

เคยเกิดปัญหานี้มาแล้ว มี 3 คอลัมน์ถูกเพิ่มตรงใน Dashboard โดยไม่มีไฟล์
ทำให้คนที่สร้างฐานข้อมูลใหม่ตามไฟล์ได้ schema ไม่ตรง แล้วเว็บพัง
(ดู `docs/sql/29_missing_columns.sql` ที่เขียนย้อนหลังให้)

ตั้งชื่อไฟล์เป็นเลขถัดไปเรียงกัน และเพิ่มบรรทัดอธิบายใน `docs/sql/README.md`

## กฎทางธุรกิจที่ห้ามละเมิด

ทั้งหมดบังคับที่ฐานข้อมูล ไม่ใช่แค่ฝั่งเว็บ

1. `quantity_remaining` ห้ามติดลบ และห้ามเกิน `quantity_received`
2. `quantity_fulfilled` ห้ามเกิน `quantity_requested`
3. ห้ามจ่ายของที่ `expiry_date` เลยวันนี้แล้ว (เทียบกับวันที่ตามเวลาไทย ไม่ใช่ UTC)
4. หมวดหมู่ของที่จ่าย ต้องตรงกับหมวดหมู่ในคำขอ
5. ถ้าคำขอระบุหน่วยไว้ ต้องจ่ายจากล็อตที่หน่วยตรงกันเท่านั้น
6. คำขอที่ `fulfilled` หรือ `cancelled` แล้ว ห้ามจัดสรรเพิ่ม
7. ห้ามลบผู้บริจาคที่มีประวัติบริจาคแล้ว ให้ตั้ง `is_active = false`

### การเปลี่ยนยอดต้องผ่านฟังก์ชันเท่านั้น

`donations.quantity_remaining` · `requests.quantity_requested` ·
`requests.quantity_fulfilled` · `requests.status`

สี่คอลัมน์นี้มี trigger กันไว้ ถ้า `update` ตรงจากหน้าเว็บจะได้ error `F5:stock_locked`
ต้องเรียกผ่านฟังก์ชันในฐานข้อมูลแทน

| ต้องการทำอะไร | เรียกอะไร |
|---|---|
| จัดสรรของ | `supabase.rpc('allocate_items', ...)` |
| จัดสรรหลายล็อตในครั้งเดียว | `supabase.rpc('allocate_items_multi', ...)` |
| ยกเลิกการจัดสรร | `supabase.rpc('cancel_allocation', ...)` |
| ยกเลิกคำขอ | `supabase.rpc('cancel_request', ...)` |
| ยืนยันรับของ | `supabase.rpc('mark_delivered', ...)` |

ฟังก์ชันเหล่านี้เป็น `security definer` และใช้ `SELECT ... FOR UPDATE` ล็อกแถวไว้
กัน race condition ตอนเจ้าหน้าที่สองคนกดจ่ายจากล็อตเดียวกันพร้อมกัน
และทำงานเป็นทรานแซกชันเดียว เช่น `cancel_request` จะคืนยอดเข้าคลังให้ด้วย
ถ้าเขียน `update` เองจะได้แค่เปลี่ยนสถานะ ของที่จ่ายไปแล้วจะค้างอยู่ในระบบ

## RLS (Row Level Security)

ทุกตารางเปิด RLS หลักการคือ `staff` เห็นเฉพาะข้อมูลของศูนย์ที่ตัวเองสังกัด
`admin` เห็นทั้งหมด ส่วน `volunteer` เห็นเฉพาะงานของศูนย์ตัวเอง

ใช้ helper function `public.my_role()` · `public.my_center_id()` · `public.is_admin()`
ในการเขียน policy ทั้งสามตัวเป็น `security definer`
**ห้ามเปลี่ยนเป็นการ select จาก `profiles` ตรง ๆ ใน policy**
เพราะจะเกิด infinite recursion แล้วทั้งระบบพัง

> **อาการเวลา RLS ผิด: query ไม่ error แต่คืนค่าว่าง**
> ถ้าเจอ array ว่างทั้งที่มีข้อมูลใน Table Editor ให้สงสัย RLS ก่อนเสมอ
> อย่าไปไล่หาบั๊กในโค้ด React

## กฎการเขียนโค้ด

- ใช้ `getUser()` เสมอ **ห้ามใช้ `getSession()`** ตัดสินสิทธิ์
  เพราะ `getSession()` อ่านจาก cookie ที่ปลอมได้
- ตรวจสิทธิ์ซ้ำใน Server Action ทุกตัว แม้ `proxy.ts` จะกันไว้แล้ว
  เพราะ Server Action ถูกเรียกตรงจากภายนอกได้
- Server Component เป็นค่าเริ่มต้น ใช้ `'use client'` เฉพาะเมื่อต้องการ state
  หรือ event handler จริง ๆ และทำ Client Component ให้เล็กที่สุด
  แยกเฉพาะปุ่มหรือฟอร์ม ไม่ใช่ทั้งหน้า
- แปลงค่าว่างเป็น `null` ก่อนบันทึกลงคอลัมน์ที่เป็น nullable
- **ห้ามเขียนข้อความที่ผู้ใช้เห็นลงในโค้ดตรง ๆ** ให้ใส่ใน `lib/i18n/dictionaries.ts`
  ครบทั้ง `th` และ `en` (ถ้าใส่ `th` แล้วลืม `en` TypeScript จะฟ้องให้เอง)
- หน่วยของสิ่งของให้เลือกจาก `lib/units.ts` เท่านั้น ห้ามพิมพ์เอง
  เพราะการจัดสรรเทียบหน่วยแบบตรงตัวอักษร "แพ็ค" กับ "แพ็ก" จะกลายเป็นคนละหน่วย
- ข้อความ error ที่แสดงต่อผู้ใช้ต้องบอกว่าต้องทำอะไรต่อ ไม่ใช่แค่บอกว่าผิด
- ตอน login ห้ามแยกว่า "ชื่อผู้ใช้ผิด" หรือ "รหัสผ่านผิด"
  เพราะเป็นการยืนยันให้คนนอกรู้ว่าบัญชีนี้มีอยู่จริง
- **ห้ามสร้างข้อมูลปลอมขึ้นมาแสดง** ถ้าไม่มีข้อมูลให้แสดง `—` หรือข้อความว่าไม่มี
- **ปุ่มที่ยังทำไม่เสร็จให้ซ่อนไปก่อน** ปุ่มที่กดแล้วไม่เกิดอะไรขึ้น
  อันตรายกว่าไม่มีปุ่ม โดยเฉพาะตอนนำเสนอ

## Git

- แตก branch ใหม่ทุกครั้ง อย่าทำงานบน `main`

  ```bash
  git checkout main && git pull && git checkout -b feat/ชื่องาน
  ```

- ห้าม push เข้า `main` ตรง ๆ ให้เปิด Pull Request
- ห้าม commit ไฟล์ `.env.local` (repo นี้เป็น public)
- **commit ด้วยบัญชี git ของเจ้าของงานเท่านั้น**
  เพราะ commit log เป็นหลักฐานประเมินคะแนนรายบุคคล
- ระหว่างทำงาน ถ้าเกิน 2-3 วันให้ `git merge origin/main` เข้ามาเรื่อย ๆ
  อย่าปล่อยให้ branch ตามหลังหลายสิบ commit แล้วค่อยมาแก้ conflict ทีเดียว
- **ห้ามก๊อปไฟล์จาก main มาวางทับ** ให้ `git merge` เท่านั้น
  ไม่งั้น git จะมองว่างานของคนอื่นเป็นงานเรา และ merge แล้วอาจลบงานคนอื่นทิ้ง

## ก่อนเปิด Pull Request

```bash
npx tsc --noEmit   # ต้องไม่มี error
npm run build      # ต้องผ่าน
npm run lint
```
